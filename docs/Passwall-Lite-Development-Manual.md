## 一、项目定位与原则

### 1.1 我们在做什么

Passwall Lite 是基于 Passwall 技术基础发展、服务于个人实际用途的独立轻量代理管理方案，不是为了追上官方特性列表而存在的“功能缩水版”。

- **需求自主**：以我们的实际使用需求决定功能边界。
- **成熟优先**：能够复用官方或既有 `main` 的成熟实现，就不重新发明一套。
- **最小必要差异**：保留与上游长期协作的可能，但不能让“减少 diff”压倒实际需求。
- **可预测**：显式、直观的配置优于隐藏联动和难以解释的自动行为。
- **可维护**：关注整体结构和未来同步成本，而不是单纯减少代码行数。
- **审慎演进**：功能需要证明价值，不能为了“新”而引入。

### 1.2 上游关系

**选择性吸收，不被动跟随**。官方改进是可以借鉴的技术来源，不是 Lite 的产品路线图。每项上游变更按以下顺序判断：

1. 改动解决什么具体问题？Lite 是否存在该问题？
2. 是否符合 Lite 的目标核心与必要能力？
3. 是否有可靠性、安全性、兼容性或易用性的实际收益？
4. 是否增加依赖、隐藏行为或长期维护负担？
5. 是否有更小、更稳定、更容易测试的复用方式？

**通常优先评估**：LuCI 通用修复、OpenWrt 兼容、ACL/nftables 基础路由、防 DNS 泄漏、明确的稳定性和安全修复。
**通常不引入**：只为 Xray/sing-box 服务的新功能、新核心和复杂高级分流。
**注意**：“通常”不等于无条件；均需结合实际证据评估。

## 二、明确的功能边界

### 2.1 唯一保留的代理核心

| 核心 | 目标版本/形式 | 客户端 | 服务端 | 备注 |
| --- | --- | --- | --- | --- |
| **Shadowsocks-libev** | 独立轻量实现 | **必须保留** | **必须保留** | 用于 TCP/UDP，实际有独立 UDP 节点需求 |
| **Hysteria（原版）** | **v1.3.5**（v1 最终版本） | **必须保留** | **必须保留** | 二进制可执行文件名为 `hysteria`；**不是** Hysteria2 |

Shadowsocks-libev 仅保留已经选定的**三种现代 AEAD 密码算法**；具体准确名称、参数及实现以当前代码与实际配置检查为准，手册不在未经核实的情况下虚构列表。禁止恢复 SIP003 插件机制。

Hysteria v1.3.5 的 `udp`、`faketcp`、`wechat-video` 传输模式是既定支持目标；端口跳跃暂缓。各模式是否通过**真实数据面**测试，必须在测试表中单独记录，不得因为表单出现就宣称可用。

### 2.2 明确移除/不引入

- Xray、sing-box、Hysteria2 以及其他不属于目标范围的代理核心。
- 所有节点订阅、订阅自动更新功能。
- 所有节点分享链接**导入与导出**功能。
- Shadowsocks SIP003 插件及相关配置/调用。
- 依赖上述核心的高级复杂分流与非必要转接架构。

**节点由 LuCI 手动配置和维护**。精简时不仅删界面入口，还应检查对应配置、运行脚本、兼容分支、依赖、错误处理与迁移代码；同时不得误删仍服务于核心功能的通用组件。

### 2.3 必须保留的基础能力

- LuCI 客户端节点管理与**两类核心的服务端配置和启动运行**。
- TCP/UDP 透明代理与基础直接连接、代理、绕过/拒绝机制。
- nftables 基础转发、ACL（访问控制）、全局规则和必要的 IPv4/IPv6 能力。
- 合理的 DNS 分流与防泄漏能力。
- 本地 dnsmasq 解析、LAN 主机名、本地服务发现及 **KMS DNS SRV 记录**。
- 直观的 Main 页面、基本运行状态和必要诊断功能。

**边界规则**：简化的是不必要的功能和实现复杂性，不能以牺牲基础网络能力、服务器端功能或可用性为代价。

## 三、关键架构决策

### 3.1 TCP/UDP 必须能够选择不同节点

**已决定**：在 Main 页面直接提供独立的 `TCP Node` 和 `UDP Node`，沿用现有 `main` 分支中成熟的交互，而不重新设计或藏进二级菜单。

`UDP Node` 至少支持：

1. `Close`：不代理 UDP。
2. `Same as the tcp node`：默认跟随 TCP，减少普通用户的配置步骤。
3. 独立选择手工配置的 Shadowsocks-libev 或 Hysteria 节点；复用原有节点分组与搜索体验。

**实际使用例**：TCP 选择 Hysteria v1.3.5、UDP 选择 Shadowsocks-libev。

**技术事实（2026-10-20 Codex 静态调查）**：Lite 继承上游 `ef6edba00f49dd6273f2a4b3d0b7054fd0b1f9e5`（`luci: merge TCP and UDP node`）。Lite 将全局 TCP/UDP 统一为 `node`，并且启动、端口与防火墙路径也合并；因此**只恢复 LuCI 控件不够**。`main` 保有旧的独立节点配置。

**实施方向，不等于已完成**：复用 `main` 的节点选择器，在新版 Lite 后端以最小必要修改恢复独立进程/监听端口、TCP/UDP nftables 路由和 ACL 行为。保留现有运行机制中已被验证的部分，**不整套回滚旧版脚本**。明确覆盖节点切换、关闭、端口缓存、失败隔离和 UDP 跟随 TCP 的情况。

**迁移风险**：现有升级脚本会移除旧 `udp_node` 配置。已被删除的用户 UDP 选择无法凭代码恢复，需从备份恢复或在 LuCI 重新设置。迁移代码应在实施前专项审查。

### 3.2 DNS：下一阶段重点简化

**已决定的目标**：降低 DNS 架构复杂度，保留清楚可解释的本地解析、必要的直连/远程 DNS 路由和防泄漏行为。

背景：曾发现新安装 Windows 无法通过本地 KMS SRV 自动发现激活服务；路由器 TCP `1688` 连通，且发现 Passwall DNS 重定向规则，问题与 Smart DNS 路径存在关联风险。**目前不能据此断言 Smart DNS 就是唯一已证实根因**；需要在实际环境中做查询路径验证。

目标约束：

- **dnsmasq 的本地域名解析、本地 SRV/KMS 服务发现不能被破坏**。
- 普通 DNS、代理 DNS、防泄漏需要清晰且可测试的职责分配。
- 不保留没有明确收益的 Smart 双上游竞速、复杂 no-IP 判断及隐式切换机制（最终删除范围需先代码审查和测试）。
- **当前阶段不提前改动 DNS 架构**；先完成 TCP/UDP 功能恢复与必要回归，再专项设计 DNS 简化。

推荐验证项：`_vlmcs._tcp` SRV 解析、Windows 自动发现、LAN 内部主机名、国内外域名解析、代理开关切换、Passwall 停止时的本地 DNS、DNS 泄漏检查。

### 3.3 ACL 与防火墙

基础 nftables/ACL 是 Lite 的核心，不应因删除高级代理核心而变成不稳定的“简化空壳”。保留基础 TCP/UDP 路由、全局/ACL 选择、失败清理、缓存生命周期、必要的 IPv6 支持。

**开发约束**：单条 ACL 应在可安全回滚时允许其他规则继续处理；无法安全回滚才停止后续流程。改动时同时考虑 nftables 与仍受支持的 iptables 路径（若代码中存在），并以实际环境验证为准。

## 四、界面与易用性原则

- **常用功能一屏可见**：不能为了表面简洁而让用户进入无意义的二级页面。
- **优先复用 LuCI 原有成熟控件**：尤其是 `main` 中已存在的 TCP/UDP 节点下拉、`Close`、跟随 TCP、协议分组与搜索。
- **避免额外依赖和自造 UI**，除非原有控件确实无法满足需求。
- **不以 CSS 隐藏功能掩盖 Bug**；应找出造成异常的 DOM、样式或资源原因。

### 已发现、未定位完成的 UI Bug

Lite 中部分带候选值的可编辑输入框右侧出现灰色方块；普通下拉框箭头正常。涉及 `Group Name`、`URL Test Address` 及 TCP/UDP 多个端口配置字段。禁用浏览器缓存并强制刷新后仍存在。

**已确认（Codex 静态比对）**：这些字段使用 `Value` + `o:value()`；与 `main` 的字段定义基本相同，未发现 Lite 为这些控件自建按钮或直接引用专门图标文件的证据。
**尚未确认**：具体设备上的 LuCI 框架、主题、CSS、资源或 DOM 渲染根因。
**下一步**：比较两台设备同一控件的 Elements/Computed Styles、点击后是否展开、Console/Network 错误、LuCI 与主题实际版本。不要未经证据直接改 CSS。

### 6.2 每个开发任务的标准流程

1. **明确目标与不变量**：要解决什么；哪些不能被破坏。
2. **先调查**：核对当前分支/工作区、现有架构、`main` 与上游参考实现。
3. **提出方案**：最小必要变更、文件范围、依赖与测试计划；区分事实、假设、建议。
4. **确认后修改**：避免 Codex 在“只读调查”阶段擅自编辑、提交或推送。
5. **静态与自动测试**：语法、配置生成、脚本、ACL/防火墙相关测试。
6. **VMware 数据面验收**：确认真实 TCP、UDP、DNS、ACL 行为，而不仅是 GUI 显示或 `RUNNING` 状态。
7. **检查差异并提交**：看 `git diff`、`git status`，按阶段提交；推送前确认分支和远端。
8. **更新开发手册与决策记录**：标记已完成、未验证、发现的新约束。

## 七、可复用测试环境与验收标准

### 7.1 VMware 测试基线

已搭建 VMware Workstation OpenWrt/ImmortalWrt 测试环境，使用与真机类似的多网卡网络分配：第一网口 LAN，其余网口按镜像默认 WAN 配置。先前 VMnet2/LAN 测试与客户端通信、WAN DHCP 获取以及上网已验证可用。目标是**以后替换镜像后尽量不用重配虚拟网络**。

### 8.2 B3.3-3 依赖契约（已冻结，未接入）

- 契约全文见 [B3.3-3 冻结节点 SOCKS/DNS 依赖契约](passwall-b3.3-3-dependency-contract.md)。
- 核心原则：DNS 代理依赖默认归属**当前作用域 TCP 节点**实例，禁止隐式借用 UDP 节点；首批只适配 `dns2socks` 与必要的 dnsmasq 路径；ChinaDNS-NG/SmartDNS 完整适配留待后续且不支持组合必须明确拒绝；SOCKS listener、透明能力、实际外层连接三类证据分别验证；依赖失败即拒绝发布，不允许静默降级；已发布实例不可变。
- 阶段划分：**3B** 依赖解析与只读核验；**3C** `dns2socks` + dnsmasq 最小衔接；**3D** 组合矩阵、拒绝发布与 B4 交接。三者均不接入生产入口。

### 8.3 进入下一阶段前需人工决定

1. `passwall_fw_check_dns` 的 `socks` 分支目前会遍历 TCP 与 UDP 实例，存在借用 UDP 节点 SOCKS 的可能；需决定收敛方式（契约 7.1）。
2. 首批不覆盖 `dns_mode=udp/tcp`，但生产当前允许；B4 切换默认入口前需决定“先适配”还是“显式拒绝并提示改配置”，否则构成功能回归。
3. DNS helper 与实例的回收时序、`ss`/inet-diag 依赖的安装责任，需在 3C/集成阶段明确。

## 九、明确区分“事实、决策、假设、未完成”

本手册与以后所有开发报告统一使用以下标记：

- **[决策]**：已经达成共识的需求与原则；改变前必须讨论。
- **[已确认·代码]**：由文件、提交、调用链、静态检查支持。
- **[已验证·运行]**：附测试环境和实际运行证据。
- **[待验证]**：尚未做真实检查，不能包装成完成。
- **[假设]**：有迹象但根因未证实。
- **[计划]**：提议的步骤，不表示已修改代码。

尤其避免以下混淆：

1. 服务状态显示 `RUNNING` ≠ 流量已走预期节点。
2. UI 选项存在 ≠ 后端完整支持。
3. 某核心客户端可连 ≠ 服务端及全部传输模式可用。
4. DNS 重定向与 KMS 故障同时存在 ≠ Smart DNS 根因已被严格证实。
5. 分支静态对比无差异 ≠ 两台固件的 LuCI 运行环境相同。
6. 代码提交/推送成功 ≠ VMware/实体机回归测试通过。

## 十、维护本手册的规则

- **单一事实来源**：本文件是开发原则与已确认决策的归档基线。仓库代码与实际测试记录仍是技术状态的最终证据；不一致时先调查再改文档。
- **版本化维护**：重大方向、功能边界或架构决策改变时，更新版本与决策记录；日常进度更新日期和状态即可。
- **每轮开发结束更新**：追加已经完成的事项、commit、测试结果、遗留风险，及时删除过期的“当前状态”。
- **不伪造验证**：不能访问仓库或测试机时，明确说明是来自维护者/Codex 的报告。
- **便于跨对话恢复**：新会话先提供本手册，并核对最新 Git/测试状态；不用依赖 AI 的跨会话记忆。
- **文档结构保持稳定**：不为每次小改动随意改变路径，便于 VS Code、Codex、GitHub 和以后持续引用。
