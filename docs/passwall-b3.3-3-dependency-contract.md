## 一、范围与不变量

### 1.1 本阶段要解决什么

B3.3-2 已经能让冻结节点在隔离环境中完成"快照 → 端点 → 实例 → 监听能力"的核验，但**没有回答 DNS 该依赖谁**：

1. 全局/ACL 作用域在 TCP 与 UDP 选不同节点时，`dns2socks` 应该连哪个实例的 SOCKS 端口？

本文件冻结这些问题的答案，并划分 B3.3-3B/3C/3D 的实施边界。**冻结的是契约，不是实现。**

## 二、已批准原则

以下 12 条为人工批准的原则，是本阶段不可协商的约束。每条给出落地要求与当前代码依据。

### 2.1 [决策] DNS 代理依赖默认归属当前作用域的 TCP 节点

- DNS 代理依赖（`dns2socks` 所连的 SOCKS 端点）默认归属**当前作用域**（`global` 或具体 ACL）的 **TCP 节点实例**。
- **禁止隐式借用 UDP 节点**：作用域 TCP 协议关闭或失败时，不得改用该作用域 UDP 节点实例的 SOCKS listener。
- 作用域 TCP 协议不可用时，DNS 依赖判定为**不可满足**；调用方必须拒绝发布该作用域的 DNS/依赖能力。
- 不属于"降级"的合法情况：用户显式把 DNS 配成本地/直连模式（`local` 等），这是配置语义，不是代理依赖。

依据（[已确认·代码]）：

- 全局 SOCKS listener 由 `run_socks flag=TCP node=$NODE` 创建，并发布为 `GLOBAL_SOCKS_server="127.0.0.1:$GLOBAL_SOCKS_port"`（`app.sh:531`、`app.sh:535-537`）；`start_dns` 的 `dns2socks` 分支直接消费该变量，为空即拒绝（`app.sh:796-799`）。
- 全局端点发布要求 `GLOBAL_SOCKS_server` 非空（`app.sh:1353-1358`），即现有生产已经把"DNS 依赖"和"TCP 节点实例"绑在一起。
- ACL 侧 `run_dns2socks` 使用本 ACL 实例的 `socks_port`（`app.sh:1147-1148`），而该文件由 ACL 实例在创建时写入（`acl_nodes.sh:301`、`acl_nodes.sh:311`）。

### 2.2 [决策] 首批冻结适配范围仅 `dns2socks` 与必要的 dnsmasq 路径

- 首批只适配：`dns_shunt=dnsmasq` + `dns_mode=dns2socks`（全局与 ACL 均限此组合）。
- "必要的 dnsmasq 路径"指：把 dnsmasq 上游指向 helper 监听所需的生成输入（`server=<TUN_DNS>`、`no-resolv`、保留本地域名/SRV 与 LAN 主机名的过滤规则），**只冻结生成输入，不改生产 dnsmasq 配置**。
- 其余已存在但不在首批范围的后端组合，一律**明确拒绝发布**，不得替换成 `dns2socks` 顶替：

| 作用域 | 现有代码允许的组合（`app.sh:163-182`） | 首批适配 | 处理 |
| --- | --- | --- | --- |
| global | `dnsmasq:udp` | 否 | 明确拒绝（B3.3-3D/B4 评估） |
| global | `dnsmasq:tcp` | 否 | 明确拒绝 |
| global | `dnsmasq:dns2socks` | **是** | 适配 |
| global | `chinadns-ng:udp` / `:tcp` / `:dns2socks` | 否 | 明确拒绝（完整适配留待后续） |
| global | `smartdns:socks` | 否 | 明确拒绝（完整适配留待后续） |
| acl | `dnsmasq:dns2socks` | **是** | 适配 |
| acl | `chinadns-ng:dns2socks` | 否 | 明确拒绝 |

### 2.3 [决策] ChinaDNS-NG、SmartDNS 完整适配留待后续，不支持的组合必须明确拒绝发布

- 不接受"先跑起来再说"：未适配后端不得进入依赖就绪状态。
- 拒绝必须是**显式、可诊断、可定位**的：返回确定原因码并记录作用域与后端组合，不得只写一条通用失败日志。
- 拒绝发生在**依赖解析 / 阶段 A 预检**，早于任何 helper 启动、端口分配或缓存发布。
- 3C 的后端支持性判断与外部依赖预检同样必须在**分配 helper 端口之前**完成（阶段 A）；预检失败不得留下可被误认为有效的运行绑定或 `dep_ready` 记录（见 4.1、6.3）。
- 本条的"预检先于端口分配"只约束**后端支持性与外部依赖能力**。dnsmasq 片段的**实际有效性**由冻结端口派生，只能在端口分配后验证（阶段 B），其失败同样拒绝发布，但不属于"后端不支持"类别（见 2.7、4.2）。

### 2.4 [决策] 必须分别验证 SOCKS listener、透明代理能力与实际外层连接

三类证据不可互相替代，也不可合并成一个"ready"。下表在前三类之外补充 **helper 身份/监听归属** 与 **真实 DNS 查询** 两类证据，`dep_ready` 必须同时具备全部五类，并另须通过 3C 的**派生配置验证**门禁（见本节末条）；五类证据的分离原则相同：

| 能力 | 定义 | 可接受的证据 | 不可接受的替代 |
| --- | --- | --- | --- |
| SOCKS listener | 该实例确实在声明的地址/端口接受 TCP 控制连接 | 真实 SOCKS5 方法协商成功（非仅 connect 成功） | `socks_port` 文件存在、进程存活 |
| 透明代理能力 | 该实例具备该协议/地址族的透明入口 | B3.3-2 `verify DIR [seal] FAMILY PROTO [PORT]` 的 socket + options 核验 | 端口字符串、`/proc/net/tcp` 单表、日志 |
| helper 身份与监听归属 | helper 进程身份可核验，且其 **DNS 监听端口**确属该进程 | PID/birth/可执行文件/命令行摘要与记录一致，且监听由该 PID 持有 | PID 存在、端口被占用、进程名匹配 |
| 实际外层连接 | 冻结端点真的能出站 | 真实数据经该实例到达冻结端点 | 配置里有 `server`、DNS 解析成功 |
| 真实 DNS 查询 | 端到端：请求经**指定** SOCKS 实例出站并返回预期响应 | 真实查询 + 响应内容符合预期 + 独立的出站路径证据 | 查询返回即算通过、仅本地缓存命中 |

- SS UDP-only 实例的 SOCKS **TCP 控制连接是辅助能力**，不得据此发布 TCP 透明代理能力（与 B3.3-2 的既有结论一致）。
- 五类证据的通过状态必须分别记录，任一缺失即依赖不就绪。
- **证据的产生阶段与顺序不同**：SOCKS listener 与透明能力在 3B 核验（只读）；helper 身份、实际外层连接、真实 DNS 查询在 3C 核验，且顺序固定为“身份 → 外层连接 → DNS 查询”（见 3.3）。因此 3B 最多只能产出“前置能力已核验”的候选，**不得宣称完整 ready**（见 3.5）。
- **派生配置验证是独立门禁，不并入上表五类证据**：dnsmasq 片段由**冻结的** helper 监听地址/端口派生，只能在端口分配后验证（见 2.7、3.3、4.2）。它证明"派生配置可被 dnsmasq 解析"，既不证明"请求经过 helper"，也不证明"能出站"，因此不能替代任何一类证据；反之五类证据也不能证明片段有效。`dep_ready` 需要五类证据**加**该门禁。
- **DNS 查询成功不得单独视为外层连接证明**：两者必须分别取证；外层连接证据不能由查询成功、日志或配置推断。
- 任何阶段都不得用端口存在、进程存活、配置里有 `server` 或 DNS 解析成功代替实际外层连接证据。

### 2.5 [决策] Shadowsocks-libev 仅支持三种 AEAD

`aes-128-gcm`、`aes-256-gcm`、`chacha20-ietf-poly1305`（[已确认·代码] `util_shadowsocks.lua:6-8`；生成器对其它方法直接报 `unsupported or missing method`）。

- 依赖层不得接受流密码、`2022-blake3-*` 或空方法。
- 该约束由既有生成器执行；B3.3-3 不重复实现白名单，只在依赖记录中保留实际方法以供诊断。

### 2.6 [决策] Hysteria 使用原版 v1.3.5，不是 Hysteria2

- 依赖契约只承认 `type=Hysteria`（v1.3.5，可执行文件 `hysteria`）与 `type=SS`（SS-libev）。
- `Hysteria2`、`Xray`、`sing-box`、`Socks` 服务类型继续被 `check_node_supported` 拒绝（`app.sh:143-161`），不得因 DNS 依赖需要而放宽。
- [待验证] 目标设备上 `hysteria` 二进制版本是否为 v1.3.5，仍属 B5 验收项；B3.3-3 不据版本号做隐式降级。

### 2.7 [决策] 冻结静态配置，显式校验必要的外部静态依赖

- **逻辑依赖输入**（节点、端点、实例路径、SOCKS 地址/端口、远端 DNS、缓存开关）必须来自**同一份快照 + 同一份实例 binding**。
- **helper 运行参数**（监听地址/端口）在 3C **阶段 B** 一次性分配并冻结；3B 不预分配、不写入未确定值。
- **顺序约束（两阶段，消除"配置验证依赖端口"的时序歧义）**：
  - **阶段 A｜端口分配前**：后端组合受支持判断 + 外部依赖预检（存在性、可执行性、命令行与所需能力探测；对 dnsmasq 只探测**配置验证能力是否可用**，不校验依赖端口的实际片段）。任一项失败即拒绝：**不分配 helper 端口、不创建运行绑定、不生成片段、不启动进程、不发布 `dep_ready`**。
  - **阶段 B｜端口分配后**：分配并冻结监听地址/端口 → 生成 dnsmasq 片段 → 在隔离环境用**实际片段**完成配置验证 → 启动 helper。片段验证失败同样不得发布 `dep_ready`，并按 5.2 逆序清理已创建资源。
  - **两阶段的失败后果一致（拒绝发布），差别只在"是否已产生运行绑定"**：阶段 A 失败时无资源需清理；阶段 B 失败时按 5.2 逆序清理，清理不可确认则保留记录与重试信息。阶段 A 不得因"片段尚未生成"而跳过依赖探测，阶段 B 也不得重复阶段 A 的探测。
- 冻结完成后，helper 启动与重试**不得**二次读取 live UCI，不得重新解析域名或改写端口。
- 外部静态依赖（二进制、诊断工具、内核能力）必须**显式校验**，缺一即拒绝，不得"先启动再观察"。
- helper 启动之后的身份、外层连接或 DNS 查询失败，仍须按既有生命周期契约安全清理已创建的运行资源；不得为了“避免分配端口”而跳过清理。

### 2.8 [决策] 已发布实例不可变

- 实例目录一旦发布，其 `config.json`、`binding.json`、`bound.identity`、`bound.capabilities`、`socks_port` 不得原地改写。
- 端点、配置摘要、地址族或代次变化必须创建**新实例新目录**；同代重试复用原固定 IP。
- 依赖记录只能引用已发布实例，不得为了让依赖成立而回写实例文件。

### 2.9 [决策] 复用 B2/B3.1/B3.3-2 的实例所有权、共享与回收机制

- 只使用既有实例目录、`ACL_*_instance` 引用、`owner`/`verify` 核验、`0/2/1` 错误分类。
- **不引入第二套生命周期管理系统**：不新增引用计数器、不新增成功缓存框架、不新增守护/重启器、不新增独立 DNS 资源管理器。
- DNS helper 进程由依赖记录引用，回收判断沿用实例"最后使用者清理"规则；不新建独立资源管理器或独立引用计数。helper 与实例的具体回收时序见 5.2（[待验证]）。

### 2.10 [决策] 依赖失败即拒绝发布，不允许静默降级

禁止的降级方式（非穷举）：

1. TCP 不可用 → 改用 UDP 节点 SOCKS。
2. `dns2socks` 缺失 → 改用直连 DNS 或系统 dnsmasq 直连上游。
3. helper 启动失败 → 保留旧端口缓存或旧 helper 继续服务。
4. 实例已换代 → 继续用旧 `socks_port` 数字。
5. 未适配后端 → 替换成 `dns2socks`。
6. 诊断工具缺失 → 退回"进程存活即就绪"。

以上任一情形都必须使候选不可发布，并保留可诊断原因；不得用"服务仍可用"掩盖依赖未满足。

### 2.11 [决策] SS 双栈 UDP 能力不足时保持拒绝发布

- 单个 `ss-redir` 的 IPv6 UDP socket 为 `V6ONLY=1` 时，不得宣称双栈 UDP（B3.3-2 实测矩阵已拒绝该组合）。
- 拒绝是**安全降级**，不是把 SS 限制为 TCP 核心；IPv4/IPv6 单族仍可承担 TCP/UDP。
- 不得为了凑出双栈而放宽 `V6ONLY` 证明、改用端口字符串判断或伪造 socket 证据。

### 2.12 [决策] B3.3-3 不接入正式生产入口

- 不修改生产 DNS、防火墙、LuCI 运行行为；不改 `start()` 调用链。
- 新增适配器只能由测试入口或显式开关调用，默认不可达。
- 生产切换仍属 B4（含写入隔离、迁移、默认配置）与 B5（目标设备验收）。

## 三、依赖模型

### 3.1 作用域、节点与实例

| 作用域 | 依赖的节点 | 依赖的实例 | 需要的 listener | 说明 |
| --- | --- | --- | --- | --- |
| `global` | 全局 TCP 节点 | 该节点的全局实例 | 该实例原生 SOCKS（TCP） | UDP 节点实例不参与 DNS 依赖 |
| `acl/<sid>` | 该 ACL 的 TCP 节点 | 该 ACL 的 TCP 实例 | 该实例 `socks_port` | 继承全局时，依赖的是全局 TCP 实例 |
| `acl/<sid>`（仅 UDP） | 无 | 无 | 无 | DNS 依赖不可满足，必须拒绝 |

- **布局无关性**：`combined`（TCP=UDP）与 `split`（TCP≠UDP）在依赖判定上等价——只看 TCP 侧。
- **继承语义**：ACL `use_global_config=1` 时，依赖链指向全局 TCP 实例，不读 ACL 自己的节点字段（与 B3.1 的继承规则一致）。
- **失败协议不补齐**：全局 TCP 失败时，ACL 继承得到的是"TCP 缺失"，依赖不可满足，不得从 UDP 或旧缓存补回（B3.1 `passwall_acl_protocol_state` 已返回 `failed/2`）。

### 3.2 依赖记录（最小字段集）

依赖解析结果是一个可核验记录，不是布尔"ready"：

| 字段 | 含义 |
| --- | --- |
| `scope` | `global` 或 `acl:<sid>` |
| `generation` | 快照代次（来自 B3.3-1） |
| `node_id` / `node_type` / `node_method` | TCP 节点身份与算法（诊断用） |
| `instance_dir` | 已发布实例绝对路径 |
| `socks_addr` / `socks_port` | 来自该实例，不得来自节点共享缓存 |
| `family` | 依赖校验使用的地址族 |
| `state` | `dep_resolved` / `dep_validated` / `dep_ready`（见 3.5；不复用协议状态 `ready/failed/closed`） |
| `reason` | 拒绝/失败原因码（见 3.4） |

- 记录本身**不是** `dep_ready` 证明；每次消费前必须按 3.5 的"`dep_ready` 消费前复核"重新核验（与 B3.3-2"`bound.capabilities` 只记录 seal 时通过的能力"一致）。
- 3B 产出的 `dep_resolved` / `dep_validated` 是**候选/诊断记录**，不构成已发布的运行依赖，也不得落盘为消费者可用的 ready 记录（见 3.5）。
- 记录不得包含密码、PSK、认证串或完整配置内容；只保留路径、摘要与端口。
- **记录不包含 helper 监听端口**：该端口在 3C **阶段 B** 才分配，属于运行绑定而非逻辑依赖（见 3.5、4.1）。

### 3.3 核验顺序与阶段归属

**3B（只读，产出候选）**

1. 快照仍新鲜（`passwall_snapshot_check`）。
2. 作用域解析出 TCP 节点（B1 解析结果，非 live UCI）。
3. 定位该节点在本代次的已发布实例；无实例即拒绝。
4. 实例身份核验：`owner` + `verify`（PID/birth、可执行文件、GID、socket、options）。
5. SOCKS listener 核验：真实 SOCKS5 协商。

1–5 全部通过 → 记录状态最高为 `dep_validated`（候选依赖 + 前置能力证据）。任一步失败立即返回，不做下一步，不产生任何运行绑定。

**3C（阶段 A 预检 → 阶段 B 冻结、配置验证与启动 → 端到端证据）**

*阶段 A：端口分配前的预检（失败即拒绝，不产生任何运行绑定）*

1. 确认后端组合受支持（2.2 表）。
2. 校验必要的外部依赖及命令行能力（4.2 阶段 A，按作用域区分强制依赖）：存在、可执行、所需参数与能力探测。**dnsmasq 在此只确认"配置验证能力可用"，不校验依赖端口的实际片段。**
3. 阶段 A 任一项失败 → 按 3.4 返回原因码并拒绝：**不分配 helper 端口、不创建运行绑定、不生成片段、不启动任何进程、不发布 `dep_ready`**。

*阶段 B：端口分配后的冻结、配置验证与启动（失败仍须清理已创建资源）*

4. 分配 helper 端口，冻结运行参数（输入为 3B 的 `dep_validated`）。
5. 依冻结的监听地址/端口 + 同一快照生成 dnsmasq 片段，并在**隔离环境**用该实际片段完成配置验证（4.2 阶段 B）；不得修改生产 dnsmasq 配置或 `/etc/config/dhcp`。失败 → `dns_dep_config_invalid`，不发布 `dep_ready`，按 5.2 逆序清理（此时 helper 尚未创建，只需撤销运行绑定与端口预留）。
6. 启动 helper，**立即**核验精确进程身份、监听归属与配置绑定（5.2）。
7. 验证实际外层连接：真实数据经该实例到达冻结端点。
8. 真实 DNS 查询验收，须覆盖两层且**两层都通过**：(a) **L1**——直接查询 Helper 自身，确认请求经**指定** SOCKS 实例出站并获得预期响应；(b) **L3**——由冻结片段驱动的**隔离** dnsmasq 实例发起真实查询，确认请求经该 dnsmasq 到达**预期 Helper** 并返回符合预期的响应。**L1 通过不得替代 L3。**
9. 全部必要检查通过后，才允许发布 `dep_ready`；其必要条件是 **L1（第 8a 步）、L2（第 5 步）、L3（第 8b 步）三层全部通过**（见 3.5、6.3）。

- **顺序不可交换**：第 1–3 步失败不得分配端口、不得创建运行绑定；第 5 步失败不得启动 helper；第 6 步失败不得继续第 7、8 步；第 7 步失败不得用第 8 步的查询成功顶替。
- **阶段 A 与阶段 B 的失败后果相同（拒绝发布），差别只在"是否已产生运行绑定"**：阶段 A 失败时没有资源需要清理；阶段 B 失败时按 5.2 逆序清理，清理不可确认则保留记录并返回 `1`。
- 任一环节失败均不得发布 `dep_ready`，并须按既有生命周期契约安全清理已创建的运行资源（见 5.2）。
- **3B 不得写 `dep_ready`**；3C 不得跳过 3B 的前置核验直接绑定。
- **三层必要性**：L2 在第 5 步、L1 在第 8a 步、L3 在第 8b 步；三层**均为** `dep_ready` 发布的必要条件，**不得以 L1 或 L2 替代 L3**（反之亦然）。L3 只是既有第 8 步的验收内容，**不新增生命周期状态、不新增架构层、不新增资源管理器**。
- **禁止以弱证据顶替**：端口存在、进程存活、DNS 解析成功、配置里出现 `server`，均不能替代第 7 步；第 8 步成功也不能替代第 7 步；第 5 步的片段验证也不能替代第 7、8 步（反之亦然）。

### 3.4 原因码（建议，3B 定稿）

| 码 | 含义 |
| --- | --- |
| `dns_dep_no_tcp` | 作用域无可用 TCP 协议（关闭/失败） |
| `dns_dep_backend_unsupported` | DNS 后端组合不在首批范围 |
| `dns_dep_no_instance` | 无已发布实例 |
| `dns_dep_stale_generation` | 实例属于旧代次或快照已过期 |
| `dns_dep_identity` | 身份核验失败（PID/birth/可执行文件/GID） |
| `dns_dep_socks` | SOCKS listener 不可用或协商失败 |
| `dns_dep_tool_missing` | 必要外部静态依赖缺失或命令行能力不足（3C 阶段 A 第 2 步；含 dnsmasq 配置验证能力不可用） |
| `dns_dep_config_invalid` | 依冻结监听地址/端口生成的 dnsmasq 片段在隔离环境验证失败（3C 阶段 B 第 5 步） |
| `dns_dep_helper_start` | helper 进程未能启动或启动后立即退出（3C 第 6 步，早于身份核验） |
| `dns_dep_outer` | 实际外层连接失败（3C 第 7 步） |
| `dns_dep_dns_query` | 真实 DNS 查询未达预期（3C 第 8 步）：L1（直接查询 Helper）或 L3（隔离 dnsmasq 完整衔接）失败共用此码，但诊断必须标明失败层 |

### 3.5 逻辑依赖与运行绑定（状态模型）

依赖不是一层对象，必须区分"能解析出依赖"与"helper 真的跑起来并能出站"：

| 层 | 内容 | 产生阶段 | 是否含 helper 端口 |
| --- | --- | --- | --- |
| 逻辑依赖解析结果 | 作用域、代次、TCP 节点、实例路径、SOCKS 端点、地址族 | 3B（只读） | 否 |
| 前置能力证据 | SOCKS listener 协商 + 透明能力 socket/options | 3B（只读） | 否 |
| helper 运行绑定 | 监听地址/端口、完整命令行 | 3C（阶段 A 预检通过后） | 是 |
| 派生配置验证 | 由冻结监听地址/端口生成的 dnsmasq 片段在隔离环境通过实际配置验证 | 3C（阶段 B：分配后、启动前） | 是（随绑定） |
| 端到端证据 | helper 身份/监听归属、实际外层连接、真实 DNS 查询 | 3C（启动后） | 是（随绑定） |

对应三个状态：

| 状态 | 含义 | 可否被消费者使用 |
| --- | --- | --- |
| `dep_resolved` | 已解析出候选依赖，尚未完成前置核验 | 否 |
| `dep_validated` | 前置能力核验通过，但尚无完整运行绑定及端到端证据 | **否** |
| `dep_ready` | 前置能力、派生配置验证、helper 身份/监听归属、实际外层连接与真实 DNS 查询全部通过；其中真实 DNS 查询须 **L1 与 L3 同时通过** | 是（消费前仍须按本节"消费前复核"重新核验） |

**三层 DNS 验收与 `dep_ready` 的必要条件**

| 层 | 内容 | 对应 3C 步骤 | 失败原因码 |
| --- | --- | --- | --- |
| L1 | Helper 自身真实 DNS 查询通过（经**指定** SOCKS 实例） | 第 8 步 (a) | `dns_dep_dns_query` |
| L2 | 由冻结参数生成的 dnsmasq 配置片段通过验证 | 第 5 步 | `dns_dep_config_invalid` |
| L3 | 隔离 dnsmasq 实例经**指定** Helper 完成真实 DNS 查询 | 第 8 步 (b) | `dns_dep_dns_query` |

- 三层**均为** `dep_ready` 发布的必要条件，缺一不可；**L1 或 L2 通过不得替代 L3**，L3 通过也不得替代 L1 或 L2。
- L3 只是既有第 8 步验收的一部分，**不新增生命周期状态**（仍只有 `dep_resolved` / `dep_validated` / `dep_ready`）、**不新增架构层或独立资源管理器**；`dep_ready` 的观察结果仍只有"已发布 / 未发布"。
- L1 与 L3 共用 `dns_dep_dns_query`，但诊断记录必须写明**失败层（L1 / L3）**，不得只写一条通用 DNS 失败（与 2.3 的"可诊断、可定位"一致）。

**状态持久化边界**

- `dep_resolved` 与 `dep_validated` 是 **3B 的候选结果/诊断状态**，不代表已经发布的运行依赖；3B **不写**可供消费者使用的 ready 记录，**不引入新的持久化成功缓存**。
- `dep_ready` 只能由 3C 在完成其全部 9 步（见 3.3）后发布；发布位置属运行绑定层（作用域目录），不得写入已发布实例目录（见 5.2）。
- 依赖失败继续通过 3.4 原因码、函数返回值与既有 `0/2/1` 分类表达；不新增 `dep_failed`、`dep_closed` 或新的生命周期状态机。
- 失败清理无法确认时，按既有契约保留必要的所有权记录与重试信息；**不得为了清除失败状态而误删记录，或释放仍被其他使用者引用的实例**。

**`dep_ready` 消费前复核（消费契约）**

`dep_ready` 是"发布时成立"的记录，不是"永远成立"的授权。每次消费前至少重新核验以下五项：

| # | 复核项 | 判据 | 现状 |
| --- | --- | --- | --- |
| 1 | 快照与 generation 仍有效 | `passwall_snapshot_check` 通过，记录中的 `generation` 与当前快照一致 | [待验证]（依赖既有快照检查） |
| 2 | 引用的实例身份与代次一致 | 记录中的 `instance_dir` 仍指向该节点该代次的已发布实例，`bound.identity` 摘要一致 | [待验证]（复用 `owner`/`verify`） |
| 3 | SOCKS 地址/端口仍归属指定实例 | 记录中的 `socks_addr`/`socks_port` 与该实例当前 `socks_port` 及 meta 一致，未被其他实例或进程替换 | [待验证] |
| 4 | helper 身份与记录一致 | PID/birth、可执行文件绝对路径、命令行摘要、作用域、实例路径、依赖摘要逐项比对 | [待实现]（`ln_run` 不返回 PID、无配置摘要，见 5.2 第 7 项） |
| 5 | helper 监听仍由预期进程持有 | 监听地址/端口/协议与冻结运行绑定一致，且 socket 属于该 PID | [待实现]（同第 4 项） |

- 任一项不一致 → 视为依赖不成立：按 3.4 原因码 + 既有 `0/2/1` 拒绝消费，**不得按端口或进程名"认领"**。
- 第 4、5 项当前**不具备实现基础**，3C 必须在既有记录格式上补齐（[待实现]）；在补齐前，**不得宣称已具备消费前复核能力**。
- 上述五项是"记录仍成立"的检查，**不能替代** 3C 首次发布前的真实外层连接与真实 DNS 查询证据；也不因复核通过而把 `dep_validated` 提升为 `dep_ready`。
- **不要求每次消费都重复执行完整外层连接与 DNS 探针**：那会把每次依赖消费变成端到端验收，成本与副作用不可接受，且与 2.9"复用既有生命周期机制"冲突。**证据失效的触发条件**（必须重新走 3C，见 5.2）：实例换代、快照换代、helper 重启、运行绑定变更、依赖摘要变化。
- 消费前复核**失败**时按失败处理，不保留"上一次复核通过"的成功缓存（与 2.9 一致）。

**术语冲突检查（[已确认·代码]）**

- 现有协议状态 `ready` / `failed` / `closed` 由 `passwall_acl_protocol_state` 与 `PW_FW_STATE` 使用（`acl_nodes.sh:91-113`、`split_firewall.sh:197-224`），描述**透明代理协议能力**；本文件的 `dep_*` 描述 **DNS 依赖**。两者命名空间不同，不得互相赋值、不得把 `dep_ready` 写进协议状态字段。
- 不设 `dep_failed` / `dep_closed`：依赖不成立时**不产生 `dep_ready` 记录**，用 3.4 原因码 + 非零返回表达；`closed` 属协议语义（协议显式关闭），不能用来表示"DNS 依赖失败"。
- `0/2/1` 分类保持不变：`0` 成功、`2` 可隔离失败、`1` 不可安全继续。依赖失败按作用域影响面映射到既有分类，不新增第 4 类，也不改变现有调用方的判断。

## 四、静态配置冻结与外部静态依赖

### 4.1 冻结清单

| 冻结项 | 来源 | 冻结阶段 | 说明 |
| --- | --- | --- | --- |
| 节点字段 | B3.3-1 快照中的完整 `frozen_node` | 3B | 不读 live UCI |
| 端点地址 | B3.3-1 `endpoint.bind` 选定的固定 IP | 3B | 同代重试不改 |
| 实例路径/配置摘要 | B3.3-2 `binding.json` / `bound.identity` | 3B | 与实例同源 |
| SOCKS 地址/端口 | 实例 `socks_port` + 实例 meta | 3B | 只读，不读节点共享索引 |
| 远端 DNS | 快照中的 `remote_dns` | 3B | 归一化后固定 |
| 缓存开关 | 快照中的 `dns_cache` | 3B | 固定，不随运行时状态变化 |
| helper 监听地址/端口 | 3C 阶段 B 分配 | 3C（阶段 B） | 3B 不得分配；分配后冻结，启动时不再改写 |
| dnsmasq 生成输入 | helper 运行绑定 + 同一快照（含 `TUN_DNS`） | 3C（阶段 B，端口冻结之后） | 只生成片段，不改生产配置 |
| dnsmasq 片段验证结果 | 隔离环境对**实际片段**的验证结论（通过/失败 + 摘要） | 3C（阶段 B，启动之前） | 只记录结论与摘要，不落盘到生产路径 |

- **3B 只冻结逻辑依赖输入**（节点、端点、实例、SOCKS 端点、远端 DNS、缓存开关），产出 `dep_resolved` / `dep_validated`。
- **3C 才产生 helper 运行绑定**（监听地址/端口、完整命令行），并把状态升级为 `dep_ready`；不得把尚未分配的端口写成"已确定值"。
- **3C 顺序（两阶段）**：阶段 A 预检（不涉及端口）→ 分配端口并冻结参数 → 生成片段 → 隔离验证片段 → 启动 helper → 身份/外层/DNS → `dep_ready`。
- **为什么片段生成与验证只能放在端口分配之后**：片段的上游指向是冻结的 helper 监听地址/端口，端口分配前不存在"完整片段"。阶段 A 因此只能确认"验证能力可用"，不能确认"片段有效"；这不构成对"预检先于端口分配"的违反——阶段 A 检查**依赖与能力**，阶段 B 检查**由冻结参数派生的产物**。
- 未采用"端口分配前用占位端口预验证"的替代方案：占位端口只能证明语法可解析，无法证明与冻结参数一致，且会产出"看似已验证"的假证据（见 4.2）。

### 4.2 必须显式校验的外部静态依赖

| 依赖 | 校验阶段 | 校验方式 | 缺失/失败后果 |
| --- | --- | --- | --- |
| `dns2socks` | A（端口分配前） | 存在、可执行，并通过版本/帮助探测确认支持所需参数形式 | 拒绝发布（`dns_dep_tool_missing`） |
| `dnsmasq`（存在性与验证能力） | A（端口分配前） | 存在、可执行；**配置验证能力**可用（`--test` 与 `--conf-file` 探测，见下） | 拒绝发布（`dns_dep_tool_missing`） |
| `dnsmasq`（片段有效性） | B（端口分配后、启动前） | 用冻结监听地址/端口生成的**实际片段**在隔离环境完成配置验证 | 拒绝发布（`dns_dep_config_invalid`）；不启动 helper，按 5.2 逆序清理 |
| `ss`（含 `--inet-sockopt`） | A | 版本/选项探测 | 拒绝发布（B3.3-2 已定） |
| 内核 inet-diag | A | 探测失败即拒绝 | 拒绝发布 |
| `ipt2socks` | A（**条件依赖**） | 仅当该作用域选定实现实际调用时，校验存在且可执行 | 仅该作用域拒绝，不影响其他作用域 |
| `nft` / `iptables` | — | 由 B3.2 负责，不在本轮 | — |

- `dns2socks` 已在包依赖中（[已确认·代码] `Makefile:34`），但**包依赖不等于运行时存在**：用户可能卸载、替换或升级；运行时校验仍必须执行。
- **预检顺序**：表中标记为阶段 A 的校验必须在**分配 helper 端口、创建运行绑定之前**完成；缺失依赖或命令行能力不足时直接拒绝，不分配端口、不写运行绑定、不生成片段、不产生 `dep_ready`。标记为阶段 B 的片段有效性校验在**端口冻结之后、启动 helper 之前**完成，失败同样拒绝发布（不启动 helper）。
- `ss` 不是 `ip-full` 的必然产物（B3.3-2 已记录），不得假定存在。
- **`ipt2socks` 按实际调用路径区分作用域**（[已确认·代码]）：
  - 全局：SS 走 `ss-redir`、Hysteria 走原生监听，均不经过 ipt2socks。`app.sh:519` 的 `run_ipt2socks` 只在 `type=socks` 回退分支（`app.sh:437`、`app.sh:444-459`）出现，而该类型已被 `check_node_supported` 拒绝（`app.sh:143-161`）。因此**全局不得因缺少 ipt2socks 而被拒绝**；B4 清理旧入口时需复核该回退分支是否仍可达。
  - ACL：SS 路径为 `ss-local` + ipt2socks（`acl_nodes.sh:336-340`），需要存在且可执行的校验；Hysteria ACL 使用原生监听，不需要。
  - 不得为了统一测试或简化判断而给全局引入无关依赖，也不得把 ACL 的条件依赖上升为全局强制依赖。

**两阶段的划分与机制**

- **阶段 A 只校验"能不能验证"，阶段 B 才校验"片段是否有效"**。dnsmasq 片段的上游指向是冻结的 helper 监听地址/端口，端口分配前无法生成完整片段，因此在阶段 A 校验片段有效性存在时序矛盾（见 2.7、4.1）。本契约不采用"占位端口预验证"。
- **阶段 A 的实际机制**：对 dnsmasq 做能力探测——确认二进制存在且可执行，并用一份**与端口无关的探针配置**（临时目录、不含 helper 上游）确认 `--test` 与 `--conf-file` 可用且返回 0。探针配置不得写入 `/etc/config/dhcp` 或任何生产路径。
- **阶段 B 的实际机制（[计划]，须在 3C 实测）**：
  1. 主判据：`dnsmasq --test --conf-file=<tmp>/dnsmasq.dep.conf`，退出码 `0` 且 stderr 无错误。`--test` 只做语法/语义检查，不监听端口、不读写 `/etc/config/dhcp`、不影响运行中的生产 dnsmasq。
  2. 加强判据（6.3 三层验收的第 3 层，不作为阶段 A 前置条件）：以临时目录 + 临时 `--conf-file` + 临时端口 + 独立 `--pid-file` 启动**隔离** dnsmasq 实例，确认其能加载该片段并在 loopback 上响应，随后立即停止并清理临时目录。
  3. 验证前后必须记录生产 dnsmasq 的 PID 与配置摘要，证明未被触碰。
- **若目标设备的 dnsmasq 不支持 `--test` 或行为异常**：阶段 A 即判定"配置验证能力不可用"并拒绝，**不得降级为"跳过验证"**，也不得改用"启动后再观察"。
- **不引入新的配置管理框架**：只使用 dnsmasq 自身的验证开关、临时目录与既有进程记录，不新增模板引擎、配置仓库或守护组件。
- **具体开关与输出格式在目标设备上的实际行为属 [待验证]**（OpenWrt 的 dnsmasq 变体可能不同）；3C 必须以实测结果固定命令形式，不得沿用推测。

### 4.3 与现有代码的差异提示

现有 `start_dns` 在 `dns2socks` 缺失时并不总是显式失败（`run_dns2socks` 直接把 `$(first_type dns2socks)` 交给 `ln_run`）。新适配层必须在启动前完成 4.2 阶段 A 的校验，并在端口冻结后、启动前完成阶段 B 的片段验证，**不能沿用这一隐式行为**；本轮不修改该生产函数。

## 五、实例不可变与生命周期复用

### 5.1 不可变的定义

对已发布实例，以下操作一律禁止：

- 改写 `config.json` / `binding.json` / `bound.identity` / `bound.capabilities` / `socks_port`；
- 复用实例目录承载新代次、新端点或新配置；
- 用旧实例路径 + 新 generation 标签"跨代复用"（B3.3-1 已明确禁止）。

允许的操作：只读核验、引用登记、在最后一个引用释放后按既有规则回收。

### 5.2 复用而非新建

| 能力 | 归属 | B3.3-3 的处理 |
| --- | --- | --- |
| 实例创建/停止 | B2 / B3.1 | 只调用，不重写 |
| 冻结端点与身份 | B3.3-1 / B3.3-2 | 只调用 `bind`/`verify`/`owner`/`compatible` |
| 共享与引用 | B2 / B3.1（`*_instance` 字段） | 只读判断，不新增计数器 |
| 错误分类 | 既有 `0/2/1` | 原样传播 |
| DNS helper 进程 | 本阶段新增适配器 | 由依赖记录引用；回收判断沿用实例最后使用者规则（时序待验证） |

- 不新增 `dns_*` 成功缓存键作为"第二套 `dep_ready` 来源"；如确需记录，只能作为实例引用下的诊断附属信息，且不得替代实时核验。
- 3B 不创建运行绑定、不落盘任何可供消费者使用的 `dep_ready` 记录；`dep_resolved` / `dep_validated` 只作为返回值与诊断信息存在（见 3.5）。
- [待验证] helper 进程与实例的回收顺序在集成时必须实测；本轮只冻结"归属"，不实现回收。

**helper 身份与生命周期（补充契约）**

1. **可验证身份**：helper 记录必须包含 PID、进程启动时间（birth）、可执行文件绝对路径、完整命令行摘要、所引用实例路径、依赖记录摘要。仅凭 PID、端口监听或进程名**不能**推断所有权。
2. **记录位置**：helper 记录、运行绑定与 `dep_ready` 记录存放在作用域运行目录（全局与各 ACL 各自目录），**不得写入已发布实例目录**（实例不可变，见 5.1），也不得复用实例内的 `process` 文件。
3. **核验时机与方式**：helper 启动后**立即**核验（3C 第 6 步），且必须先于实际外层连接与 DNS 查询。每次消费 `dep_ready` 前，按 3.5"消费前复核"读取记录并比对 PID/birth/可执行文件/命令行摘要、作用域、实例路径与依赖摘要；任一项不一致即判定失败，不得按端口或进程名"认领"。身份核验失败时**不得继续**外层连接和 DNS 查询验收，也不得发布 `dep_ready`。
4. **释放顺序**：先停止 helper 并确认其**不再使用**所依赖的 SOCKS 实例（进程已退出、监听已释放，并在可验证范围内确认无可归因于该 helper 的残留连接），再释放实例引用、交由既有"最后使用者"规则回收。顺序不得颠倒。
5. **失败保留**：验收失败时，若已创建资源能够被确认清理，返回对应非 0 分类；若停止失败、身份不明或清理结果无法确认，则保留所有权记录与精确重试信息，停止后续清理并返回 `1`。不得先删记录再杀进程，也不得把“看起来没了”当作已清理。任何失败都不得留下 `dep_ready` 记录；不得为了清除失败状态而误删记录或释放仍被其他使用者引用的实例。
6. **不得误停**：定位必须同时限定作用域目录、代次与实例路径三重条件；禁止按进程名、端口或模糊匹配批量终止其他 ACL、其他代次或无关进程。
7. **复用现状**（[已确认·代码]）：`ln_run` 记录 PID/birth/精确命令行（`utils.sh:494-532`），但不向调用方返回 PID，也没有配置摘要；ACL 实例的 `process` 记录（`acl_nodes.sh:115-131`）位于实例目录，不能直接充当 helper 记录。因此 [待实现] 3C 需在既有记录格式上补齐 helper 记录，不新建管理器。
8. **[待验证]** helper 记录与实例回收的实际时序、失败重试路径及生命周期锁内的串行性，必须在 3C/集成阶段实测。
9. 不得引入第二套引用计数、节点注册中心、后台监控器或独立资源管理器。

**阶段 B 的创建与清理顺序（补充契约）**

阶段 A 失败时**没有任何运行资源产生**，因此不存在清理问题；只有阶段 B 会创建资源，其创建与回退顺序固定如下（与 3.3 的 3C 第 4–9 步一一对应）：

| 序 | 动作（创建） | 失败时的回退（逆序） | 原因码 |
| --- | --- | --- | --- |
| 1 | 分配 helper 端口 | —（尚未产生资源，仅释放预留） | 见对应步骤 |
| 2 | 冻结运行参数、写运行绑定（作用域目录） | 撤销运行绑定与端口预留 | — |
| 3 | 生成 dnsmasq 片段（临时路径） | 删除临时片段 → 撤销绑定与端口预留 | — |
| 4 | 隔离验证片段 | 同上；**不启动 helper** | `dns_dep_config_invalid` |
| 5 | 启动 helper | 停止残留进程 → 撤销绑定 | `dns_dep_helper_start` |
| 6 | 身份/监听归属核验 | 停止 helper → 撤销绑定 | `dns_dep_identity` |
| 7 | 实际外层连接 | 停止 helper → 撤销绑定 | `dns_dep_outer` |
| 8 | 真实 DNS 查询 | 停止 helper → 撤销绑定 | `dns_dep_dns_query` |
| 9 | 发布 `dep_ready` | — | — |

- 清理一律按创建顺序**逆序**执行。第 1–4 步失败时 helper **尚未存在**，不得执行进程终止，只需撤销绑定与端口预留、删除临时片段——这也是"片段验证先于启动"的直接收益：最可能失败的配置错误不会留下任何进程。
- 第 5–8 步失败时的停止与撤销必须遵守第 4、5、6 项（释放顺序、失败保留、不得误停）。
- **清理失败或所有权无法确认时**：保留运行绑定、helper 记录与精确重试信息，**停止后续清理**并返回 `1`；不得继续发布，也不得先删记录再杀进程。
- 任何一步失败都不得留下 `dep_ready` 记录；也不得把已发布的 `dep_ready` 回写成"失败状态"（不设 `dep_failed`，见 3.5）。
- 阶段 B 的所有中间产物（临时片段、隔离验证的临时目录与临时 `pid-file`）必须在成功与失败两条路径上都被清理；残留物不得位于生产配置路径。

### 5.3 SS 双栈 UDP 的既有拒绝保持不变

- 依赖层不得把"SS 实例存在"当作"UDP 双栈可用"。
- 依赖记录中的 `family` 与实际能力不符时，按 2.11 拒绝，不尝试"降级到单族"。

### 6.2 B3.3-3B：依赖解析与只读核验

**交付**

- 未接入的依赖解析函数：输入快照、作用域、实例记录；输出 3.2 的依赖记录与 3.4 原因码，状态最高为 `dep_validated`。
- 前置能力两类核验（SOCKS listener、透明能力），复用 B3.3-2 的 `verify`/`owner`，不重写。
- 未适配后端（2.2 表）的显式拒绝路径。
- 逻辑依赖结果与 helper 运行绑定的边界（3.5）：3B 只产出前者。

**禁止**

- 启动任何 helper、写任何缓存、安装任何规则、修改 `app.sh`/LuCI/Makefile。
- 创建 SOCKS 实例、分配 helper 端口或写 helper 运行绑定。
- 把"解析成功"或"前置能力通过"写成 `dep_ready`；不引入新的持久化成功缓存。

**验收**

1. TCP 关闭/失败 → `dns_dep_no_tcp`，且**不**尝试 UDP 实例。
2. UDP-only ACL（且未显式选择本地/直连 DNS）→ `dns_dep_no_tcp`，不得借用 UDP 实例的 SOCKS。
3. **用户显式配置的本地/直连 DNS** 不进入代理依赖判定：不返回代理依赖错误，也不被当作代理依赖失败（与第 2 项明确区分）。
4. 实例换代/快照过期 → `dns_dep_stale_generation`。
5. 篡改 `socks_port` 或替换实例路径 → `dns_dep_identity` / `dns_dep_socks`。
6. 未适配后端组合 → `dns_dep_backend_unsupported`，且不产生任何进程。
7. **全局继承**：ACL `use_global_config=1` 时依赖指向全局 TCP 实例，且不读取该 ACL 自身的 `tcp_node`/`udp_node` 字段（以读取边界探针验证）。
8. **全局不受 ipt2socks 影响**：缺少 `ipt2socks` 时全局依赖解析不得因此拒绝（见 4.2）。
9. 拒绝路径不泄露密码/PSK/认证串。
10. 证据等级：静态检查 + 原生隔离测试；不得宣称数据面通过，也不得写 `dep_ready`。
11. **状态边界**：`dep_resolved` / `dep_validated` 只作为返回值与诊断信息，不写可供消费者使用的 ready 记录，不新增持久化成功缓存；失败以原因码 + 既有 `0/2/1` 表达，不引入新状态。

### 6.3 B3.3-3C：`dns2socks` + dnsmasq 最小衔接

**交付**（严格按 3.3 的 3C 顺序实现；阶段 A 与阶段 B 分开交付）

- 阶段 A 第 1–3 步：后端支持性判断与外部依赖预检（4.2 阶段 A，按作用域区分强制依赖）。**必须在分配端口之前完成**；失败即返回，不产生运行绑定、不生成片段、不启动进程。
- 阶段 B 第 4 步：在 `dep_validated` 基础上分配监听端口、冻结运行参数（SOCKS 端点、远端 DNS、监听地址/端口、缓存开关）。
- 阶段 B 第 5 步：依**冻结**的监听地址/端口生成 dnsmasq 片段，并在隔离环境用该实际片段完成配置验证（4.2 阶段 B）；片段不落盘到生产路径。
- 阶段 B 第 6 步：生成命令行并启动 helper，**立即**核验精确进程身份、监听归属与配置绑定（5.2）；失败不得继续第 7、8 步。
- 阶段 B 第 7 步：实际外层连接核验（2.4 第四类证据）。
- 阶段 B 第 8 步：真实 DNS 查询验收，须**同时**完成 L1（直接查询 Helper，2.4 第五类证据）与 L3（隔离 dnsmasq 实例经该 Helper 的完整衔接）；**L1 通过不得替代 L3**。
- 第 9 步：全部必要检查通过后，才发布 `dep_ready`；必要条件为 **L1、L2、L3 三层全部通过**（见 3.5）；发布位置为作用域运行目录，不写实例目录。
- helper 启动/核验/停止/清理适配，仅经测试入口可达；阶段 B 的创建与回退顺序按 5.2"阶段 B 的创建与清理顺序"执行。

**禁止**

- 修改生产 `start_dns`、生产 dnsmasq 配置、`/etc/config/dhcp`、LuCI、防火墙、init。
- 安装软件包、下载核心、改 Makefile。
- 依赖失败时保留旧 helper 或旧端口继续服务。
- 在未完成第 6–8 步前写 `dep_ready`；在阶段 A 预检失败后仍分配端口或创建运行绑定；在片段验证失败后仍启动 helper。
- 以 L1 或 L2 通过代替 L3 发布 `dep_ready`；以 `ss -tnp`、端口监听或单次查询返回作为 L3 的唯一证据。
- 为验证片段而对生产 dnsmasq 执行 `reload` / `restart`，或把片段写入 `/etc/config/dhcp` 或生产配置路径。
- 为清除失败状态而删除所有权记录或释放仍被使用的实例。

**验收**（按 3.3 的 3C 顺序；以下全部为 [计划]，本轮未执行、未通过）

1. **正向三层验收**：真实 `dns2socks` + 真实 B3.3-2 实例。三层是**三个独立结果**，分别记录命令、退出码与关键证据，不得合并为一行"通过"，也不得互相顶替：

| 层 | 目标 | 计划命令（示例） | 通过判据（须记录的证据） |
| --- | --- | --- | --- |
| L1 Helper 自身可用 | 真实 `dns2socks` 经**指定** SOCKS 实例完成 DNS 查询 | 启动 helper 后：`nslookup -port=<helper_port> <probe_name> <helper_addr>`（查询工具以目标设备实际可用者为准，语法须实测） | 退出码 `0` 且响应内容符合预期；`ss -tnp` 证据显示**该 helper PID** 连接的是**该实例**的 `socks_port` |
| L2 配置片段有效 | 依冻结监听地址/端口生成的片段能被 dnsmasq 实际解析 | `dnsmasq --test --conf-file=<tmp>/dnsmasq.dep.conf`；同时记录片段 `sha256` | 退出码 `0`、stderr 无错误；片段内 `server=` 指向**冻结**的 helper 地址/端口；生产 dnsmasq PID 与配置摘要前后不变 |
| L3 完整衔接可用 | 隔离运行的 dnsmasq 实例发起真实查询，请求到达**预期 Helper** 并返回符合预期的响应 | 临时目录内以 `--conf-file` + 临时端口 + 独立 `--pid-file` 启动隔离实例 → 以唯一 probe 名查询 → 停止实例 | 退出码 `0` 且响应符合预期；隔离实例 PID ≠ 生产 dnsmasq PID；**按协议分段取证**（见下方"L3 证据的协议适配"），不得只用 `ss -tnp`；临时目录已清理 |

- 三项必须分别记录命令、退出码与关键证据；**三层均为 `dep_ready` 的必要条件（见 3.5）**，L2 通过不能替代 L1/L3，L3 通过不能替代 L1。三层均使用**首次出现的唯一 probe 名**，避免缓存命中造成假阳性。
- **L3 必须使用隔离的 dnsmasq 实例与临时配置，不触碰生产 DNS**：不得 `reload`/`restart` 生产 dnsmasq，不得写 `/etc/config/dhcp`；验证前后须记录生产 dnsmasq 的 PID 与配置摘要作为"未触碰"证据。
- **L3 成功不能替代第 7 步的独立外层连接证据**：完整衔接只证明"请求经 Helper 到达 SOCKS 实例并返回"，外层连接证据仍须单独取证（2.4）。
- **L1 成功不能替代 L3**：Helper 自己能答，不等于 dnsmasq 能把请求交给它。
- 任一层失败（含 L1/L2/L3 任一失败）均不得发布 `dep_ready`。

**L3 证据的协议适配（不得以 `ss -tnp` 作为整条链路的唯一证据）**

L3 链路跨三段、涉及两种传输协议。`ss -tnp` 只覆盖 **TCP 段（Helper → SOCKS 实例）**，对 **dnsmasq → Helper 的 UDP 转发不可见**，因此必须按段分别取证：

| 段 | 协议 | 适用的证据 |
| --- | --- | --- |
| 隔离 dnsmasq → Helper | **UDP**（`dns2socks` 的 DNS 监听为 UDP；若实现同时监听 TCP，须分别记录） | `ss -unp` 核验隔离 dnsmasq 进程的已连接 UDP socket 指向 `<helper_addr>:<helper_port>`；loopback 抓包 `udp and port <helper_port>` 取得 query/response 配对；隔离实例 `--log-queries` 显示该查询被 forward 到该 upstream |
| Helper → SOCKS 实例 | **TCP** | `ss -tnp` 显示 Helper PID ↔ `socks_port`（**仅此段**，不能外推到上一段） |
| Helper 收到并处理查询 | — | 唯一 probe 名 + Helper 侧日志/计数，或抓包中同一 probe 名的 query → response 配对 |

- 四类证据均须取得，并各自绑定到上述协议段：① **socket 与进程归属核验**（UDP 侧 `ss -unp` + TCP 侧 `ss -tnp`）；② **隔离环境网络抓包**（仅 loopback，不抓生产接口）；③ **连接或数据包计数**（查询前后计数差应匹配：1 次唯一查询 → 1 次 forward → 1 条到 `socks_port` 的连接/请求）；④ **可确认指定 Helper 收到并处理**的证据（唯一 probe 名出现在该 Helper 的处理路径上，而非"某进程在监听"）。
- **设备缺少抓包能力**（无 `tcpdump` 等）时，L3 记为 **SKIP 而非 PASS**（沿用 6.4 的 SKIP 规则）；不得用"端口在监听 + 查询返回"顶替。
- **排除缓存命中造成的假阳性**：probe 名必须是**首次出现的唯一随机标签**（含随机段，避免 dnsmasq 缓存、上游缓存与 SOCKS 侧缓存命中）；隔离实例以空缓存启动；`--log-queries` 中出现 `cached` 标记的响应判为无效证据，须换名重测；并加一次**阴性对照**——Helper 未启动时用另一唯一标签查询应失败/超时，启动后以新的唯一标签重测应成功，以此证明成功响应来自该 Helper 而非缓存或其他上游。
- **不降低外层连接取证要求**：以上四类证据只服务 L3 的"完整衔接"，**不构成**第 7 步的实际外层连接证据；外层连接仍须按 2.4 第四类独立取证，L3 成功不得替代它。

2. **阶段 A 预检拒绝**（第 1–3 步）：按下表拒绝，且**未分配 helper 端口、无运行绑定、未生成片段、无 helper 进程**：

| 作用域 | 节点类型 | 缺失/不可用依赖 | 预期 |
| --- | --- | --- | --- |
| global | SS / Hysteria | `dns2socks` | 拒绝（`dns_dep_tool_missing`），无绑定 |
| global | SS / Hysteria | `dnsmasq` 缺失或不可执行 | 拒绝（`dns_dep_tool_missing`），无绑定 |

3. **片段验证失败拒绝**（第 5 步）：构造无效片段（非法上游地址、越界端口、未知指令等）→ `dns_dep_config_invalid`，**不启动 helper**、无 `dep_ready`；运行绑定与端口预留按 5.2 逆序撤销，临时片段已删除。
4. **Helper 不可用拒绝**（第 6 步）：`dns2socks` 无法启动或启动后立即退出 → `dns_dep_helper_start`；启动成功但身份/监听归属不符 → `dns_dep_identity`。两种情形均不得发布 `dep_ready`，并须按 5.2 停止残留进程、撤销绑定。
5. **身份失败**（第 6 步）：替换 PID、复用已退出进程的 PID、改写命令行或实例路径 → 核验失败，**不执行第 7、8 步**（以探针断言未发起外层连接与 DNS 查询），不发布 `dep_ready`，已创建资源按既有生命周期清理。
6. **外层连接失败**（第 7 步）→ 不得以第 8 步查询成功顶替，不发布 `dep_ready`（`dns_dep_outer`）。
7. **DNS 查询失败或不符**（第 8 步）：**L1 或 L3 任一未达预期**——查询未经指定实例出站、超时、响应不符、L3 证据不足或出现缓存命中 → `dns_dep_dns_query`（诊断须标明失败层 L1/L3），不发布 `dep_ready`；L1 通过但 L3 失败时，不得以 L1 结果发布。

9. **冻结输入**：与 live UCI 不一致时仍使用冻结输入（或按快照过期拒绝），不得读 live 值；片段中的上游地址/端口必须与冻结运行绑定逐字节一致。
10. **失败清理**：阶段 B 任一失败都不得留下 `dep_ready`；第 1–4 步失败不得产生进程；第 5–8 步失败须停止 helper 并撤销绑定；清理成功返回对应非 0 分类；停止失败或清理不可确认 → 保留记录与重试信息、停止后续清理并返回 `1`，不删除所依赖实例，不得误停其他 ACL/代次的 helper。
11. **证据等级**：真实进程 + 真实 socket + 真实查询 + 真实 dnsmasq 加载；仍不宣称生产 DNS 已切换。上述三层验收与全部拒绝测试均为 [计划]，本轮**未执行**，不得标记为已通过。
